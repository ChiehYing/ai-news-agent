Claude 的安全架構分為三個主要環境：Claude.ai 使用 gVisor 進行進程沙箱化，Claude Code 在本地使用 Seatbelt（macOS）或 Bubblewrap（Linux）提供檔案系統限制，而 Claude Cowork 則在完整虛擬機中運行。每種隔離機制都會強制限制可執行的系統資源、檔案存取與網路出口，從而防止憑證外洩與未授權的操作。此架構的設計理念是即使模型嘗試「創意」路徑，也必須通過既定的邊界檢查才能執行。這些隔離層共同構成嚴格的安全邊界，確保敏感資源不會被意外存取。

**Key Insight:** 關鍵在於通過多層次的隔離（進程沙箱、虛擬機與 egress 控制）避免任何憑證或敏感資料外洩，即使模型嘗試繞過限制也無法突破。

### 學習筆記

若你在開發需要嚴格資源限制的代理系統，可參考此多層隔離模型，透過容器或虛擬環境限制檔案與網路存取，確保 API 金鑰與內部資料不會被模型意外動作泄露。

## 3. 3 reasons a one-time MCP scan fails you

`mcp` `security` `ai` `reliability`

**來源：** DEV.to | [原文連結](https://dev.to/milo_antaeus_784320e2f2f9/3-reasons-a-one-time-mcp-scan-fails-you-4dfl)

### 摘要

文章說明一次性 MCP 掃描失效的三個主要原因：第一，工具模稜兩可的 schema 變更不會更新版本號，導致系統在使用過時的描述時仍然信任新 schema；第二，變更不會有變更日誌，因而無法辨識何時以及何種變更發生；第三，代理在審計後仍會自動信任新 schema，缺乏持續監控機制。文章建議採取持續追蹤變更歷史的方式，以避免被 rug‑pull 式的惡意變更所駭怕。這種持續監控能讓代理在變更發生時即時偵測並做出警告或回滾。此外，示範了如何使用自動化工具追蹤 schema 變更，以提升系統的可靠性與安全性。

**Key Insight:** 一次性掃描不足以應對動態變更，必須持續監控 schema 以避免信任過時或惡意的更新。

### 學習筆記

在使用 MCP 類工具時，應實作持續變更偵測與版本驗證流程，讓代理能即時得知工具 schema 的最新狀態，並根據可信的版本資訊決定是否使用。

## 9. How to stop your RAG assistant from hallucinating (a practical guide)

`rag` `ai` `llm` `tutorial`

**來源：** DEV.to | [原文連結](https://dev.to/pante5ter/how-to-stop-your-rag-assistant-from-hallucinating-a-practical-guide-2imd)

### 摘要

文章指出 RAG 幻覺的根本原因在於取回的上下文不完整或不相關，因此必須先優化排片方式，採用語義分塊而非固定字符長度，並且結合關鍵字搜索與稀疏向量檢索提升召回精度。使用重排階段（reranker）可進一步提升相關文段的排序，使得模型取得的上下文更能對應使用者查詢。此外，必須在提示中明確指示模型只能根據提供的上下文作答，並要求提供引用來源；若答案不在上下文內，則必須說明「我不知道」，避免自行猜測。建立測試集對每次變更進行驗證，追蹤 groundedness 與召回率，能確保系統持續可靠。最後，採用簡潔、可度量的流程是讓 RAG 助理真正可信的關鍵。

**Key Insight:** 正確的檢索與嚴格的「只根據上下引用」指令是防止幻覺的關鍵所在。

### 學習筆記

在構建 RAG 系統時，應使用語意與關鍵字混合檢索、reranker 排序，並在生成回覆時強制模型只引用提供的文獻，並提供來源，若不確定則回覆「我不知道」。

**Key Insight:** 離線壓縮與 Token 統計讓開發者能在不超出上下限的情況下打包大量內容，顯著提升提示效能。
