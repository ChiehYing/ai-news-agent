### 摘要

這篇文章介紹了 Gemma 4 系列模型透過量化感知訓練（QAT）實現的壓縮優化，讓模型能在日常 edge 裝置與消費級 GPU 上高效運行。文章說明了靜態激活、通道分量化、2-bit 量化以及 KV cache 最佳化等技巧，並提供了專為手機設計的量化方案，使 E2B 版僅需約 1GB 記憶即可載入。它比較了傳統的後處理量化（PTQ）與 QAT 在品質上的差異，證明 QAT 能在壓縮時保留更高的精度。最後說明了與開發者工具的整合方式，方便直接下載使用。

**Key Insight:** QAT 配合專屬行動裝置量化方案，使 Gemma 4 E2B 僅需約 1GB 記憶體即可運行，且在壓縮過程中品質損失極小。

## 2. Inside FAISS: Billion-Scale Similarity Search

`FAISS` `Similarity Search` `Vector Search` `Product Quantization`

**來源：** Hacker News | **評分：** 36 | [原文連結](https://fremaconsulting.ch/blog/faiss)

### 摘要

文章深入探討了 FAISS 在大規模相似度搜尋中的設計，從向量嵌入的概念說起，說明向量空間中相似度的衡量方式。它比較了全遍計算的高成本與利用 IVF 分區與製品量化大幅縮小資料量的做法，說明如何透過 coarse quantizer 選取有前景的細胞，以及 PQ 將向量壓縮為数位碼以降低儲存與比較開銷。文中提供互動式基準測試，展示不同索引在不同規模資料上的效能差異，並針對實務應用給予選擇建議，如僅搜尋最相關的細胞，平衡精度與速度。此外，文章指出在高維空間中使用適當的量化比特長度可顯著降低記憶體佔用，使即使是上億向量的查詢也能在普通 GPU 上完成。

**Key Insight:** IVF 將向量空間分割成 Voronoi 細胞，製品量化將向量壓縮為數位碼，使得即使上億向量的搜尋仍能在可接受的記憶體與計算範圍內完成。

### 學習筆記

在構建 RAG 或相似度搜尋系統時，可先將向量以 dense 嵌入後使用 IVF 索引劃分，再以 PQ 壓縮以減少儲存，根據查詢特性調整細胞範圍與壓縮精度，以獲得最佳效能與精度平衡。

## 6. Building a Fully-Local Research RAG on 2 GTX 1080 Ti + an RTX 3090 — 3 Gotchas

`RAG` `Local LLM` `Hybrid Retrieval` `GPU` `Ollama`

**來源：** DEV.to | [原文連結](https://dev.to/sysoft/building-a-fully-local-research-rag-on-2x-gtx-1080-ti-an-rtx-3090-3-gotchas-48dl)

### 摘要

文章說明了在兩張較舊的 GTX 1080 Ti 與一張新型 RTX 3090 上，完整離線地建置研究型 RAG 系統，並分享了三個關鍵教訓。第一，嵌入模型（如 BGE-M3）在 WSL2 環境中執行時會使 GPU 掛起，解法是將嵌入限定在 CPU 執行，避免 GPU 鎖死。第二，過大的原始上下文會造成 KV cache 超過顯存，導致推理速度驟降，解決方法是將上下文長度（num_ctx）限制在實際使用的範圍內。第三，嘗試將多卡合併成單一大模型會因 PCIe 帶寬限制而降低效能，建議將嵌入與索引作業分配給較慢的 GPU，而將推理與重排任務放在高效能卡上。最後提供了相應的配置示例與 MCP 接口說明，供想在本地環境中實作完全私密 RAG 的開發者參考。

**Key Insight:** 避免在舊型 GPU 上執行大型嵌入模型、限制 KV cache 上下文大小、以及將工作負載專業化以符合不同硬體特性，是成功部署跨卡本地 RAG 的關鍵。

### 學習筆記

在開發本地化 RAG 系統時，可將語义向量化放在 CPU 或低功耗 GPU，將向量搜尋與重排放在更強的 GPU，並注意控制上下文大小以避免記憶體溢出，這樣不僅保證穩定運行，也能發揮多卡資源的最佳效能。

## 7. When does flat-file memory beat a vector DB for your agent?

`Memory Management` `Vector DB` `Agent Design` `Retrieval`

**來源：** DEV.to | [原文連結](https://dev.to/manja316/when-does-flat-file-memory-beat-a-vector-db-for-your-agent-4bnd)

### 摘要

文章指出，對於必須在每次提示中可靠包含的「永恆事實」，使用結構化的平面檔案（如上限 200 行的索引標記文件）比向量資料庫更佳，因為它提供了 100% 的載入保證，而向量檢索僅是機率性操作，可能會因相似度不足而遺漏關鍵資訊。作者建議將固定事实以嚴格格式存於 markdown 檔案，於代理啟動時一次性讀取並加入上下文，只有在需要根據查詢動態取得的資料才放入向量 DB 检索層。此方式既避免了因索引過大而被截斷的風險，也简化了維護與編輯流程，使代理的記憶更加可預測且易於校正。此外，文中強調保持索引簡短化，讓其成為代理的第一層上下文，而檢索層僅用於變化的、可選的資訊。

**Key Insight:** 對於必須保證載入的常態資訊，直接使用上限的平面檔案索引比向量檢索更可靠，因為它消除了相似度誤判的風險，且操作簡單易於維護。

### 學習筆記

在設計代理的長期記憶架構時，應將絕對必須知道的事項以條理清晰的 markdown 文件形式儲存，啟動時一次性載入並限制總行數，僅在需要根據查詢動態擴充的部分使用 RAG 或向量檢索，從而兼顧可靠性與擴充彈性。
