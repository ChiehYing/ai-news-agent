## 1. Caddy compatibility for zeroserve: 3x throughput and 70% lower latency

`performance` `eBPF` `Caddy` `proxy`

**來源：** Hacker News | **評分：** 149 | [原文連結](https://su3.io/posts/zeroserve-caddy-compat)

### 摘要

Caddy 可以與 zeroserve 兼容，透過 JIT 將 Caddyfile 轉譯成 eBPF 並使用 io_uring 事件循環執行，達到 3 倍吞吐量與 70% 更低延遲的效能提升。這種方式允許開發者直接在 Caddyfile 中編寫自訂 eBPF 插件，例如使用 AWS SigV4 簽名後將請求反向代理至 S3。相較於傳統的 Nginx 或原生 Caddy，此方案在資源占用上顯著更低。整體展示了 eBPF 在高效網路代理中的強大潛力。

**Key Insight:** Caddy 相容性支援讓 zeroserve 能即時將 Caddyfile 翻譯成 eBPF，實現 3 倍吞吐量與 70% 更低延遲。

### 學習筆記

在構建高效網路代理或專屬代理服務時，可嘗試利用 Caddyfile 與 eBPF 的即時編譯特性，將常用的路由規則直接嵌入 eBPF，以減少延遲並提升吞吐量。

## 2. The only scalable delete in Postgres is DROP TABLE

`Postgres` `Delete` `DROP TABLE` `Scalability` `Database`

**來源：** Hacker News | **評分：** 119 | [原文連結](https://planetscale.com/blog/the-only-scalable-delete)

### 摘要

文章指出，對於大量資料的刪除操作，使用 DROP TABLE 或 TRUNCATE 是最可伸縮的做法，因為它能即時釋放磁碟空間且不會產生 dead tuple。DELETE 會保留舊版資料，增加寫入與複寫負擔，且需要額外的 VACUUM 作業。DROP TABLE 通過一次性刪除表文件和掃描緩衝區的元資料實現高速清理，僅佔共享緩衝區的小比例記憶體。作者亦討論了使用分區策略把刪除轉化為 dropping 更小的子表的方法。

**Key Insight:** DROP TABLE 是處理大規模刪除時最具擴展性的手段，因為它能即時釋放空間且不留下 dead tuple。

### 學習筆記

在設計資料清理流程時，若條件允許，可考慮將需要刪除的資料分區化，然後一次性 DROP 或 TRUNCATE 該分區，避免大量 DELETE 的效能瓶頸。

## 5. Mapping SQLite result columns back to their source `table.column`

`SQLite` `Column Metadata` `Provenance`

**來源：** Simon Willison | [原文連結](https://simonwillison.net/2026/Jun/13/sqlite-column-provenance/#atom-everything)

### 摘要

文章說明如何利用 SQLite 的 column‑metadata API（需要編譯 SQLITE_ENABLE_COLUMN_METADATA）或第三方 apsw 函式庫，取得每個結果欄位對應的原始表與欄位名稱。即使 Python 標準庫的 sqlite3 不支援此功能，使用 ctypes 也能呼叫底層 C 函式取得 table.column 訊息。這些技術可應用於 Datasette 或其他查詢工具，以提供更友好的 UI 或自動產生說明文件。了解欄位來源的方式還有助於除錯複雜的 JOIN 查詢。

**Key Insight:** 透過 apsw 或 ctypes 可取得 SQLite 查詢欄位的來源 table.column 資訊，進而建立更強大的資料可視化與文件工具。

### 學習筆記

在構建資料探索或 API 服務時，利用欄位來源機制可以自動生成文件或 UI 標示，讓使用者更直觀地了解查詢結果的結構。
