## 1. Kimi K3 Architecture Overview and Notes

`Kimi` `K3` `MoE` `Attention`

**來源：** Hacker News | **評分：** 276 | [原文連結](https://sebastianraschka.com/blog/2026/kimi-k3-architecture-notes.html)

### 摘要

Kimi K3 是繼 Kimi Linear 後的大規模開源模型，具備 2.8 兆參數規模。其新增的 LatentMoE 取代傳統 MoE，提供更佳的推理效率。整體架構採用 NoPE 取代 RoPE，並使用 attention residuals 以提升稽核表現。此外，模型在多模態支持和推理效能上皆有顯著提升。這些改進顯示出從大型模型向更有效率的 Production 版過渡的重要趨勢。

**Key Insight:** LatentMoE 的引入以及 NoPE 的全面取代，使模型在推理效率與多模態支援上達到前沿水平。

### 學習筆記

在設計代理時，可參考 Kimi K3 的 LatentMoE 與 NoPE 設計，結合 attention residuals 提升效能；同時可將 LatentMoE 與現有 MoE 框架結合，探索更高效的推理管線。

## 2. MCP 2026-07-28 Specification: transport going stateless

`MCP` `Protocol` `Stateless`

**來源：** Hacker News | **評分：** 95 | [原文連結](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

### 摘要

2026-07-28 版的 MCP 仕様將通訊協定從有狀態的 bidirectional 變為完全無狀態的 request/response 形式，移除了 handshake 及 session 機制。新版引入 Multi Round‑Trip Request（MRTR）以降續處理使用者輸入，支援以標頭路由與快取提示的 list 操作，並加強授權機制。SDK 更新包括 TypeScript、Python、Go、C# 等，提供明確的遷移說明，使開發者能夠輕鬆部署可擴展且可負載平衡的 MCP 伺服器。這次更新重點在提升可靠性與規模化部署能力。

**Key Insight:** 協定從有狀態轉為無狀態，允許任何請求獨立於之前的會話，從而實現更佳的可擴展性與可靠性。

### 學習筆記

在開發代理應用時，可直接使用無狀態的 RPC 機制，利用 MRTR 進行互動式查詢，並透過標頭路由實現有效的流量分配與授權驗證。

## 3. Kimi Linear: An Expressive, Efficient Attention Architecture (2025)

`Kimi` `Linear` `Attention` `MOE`

**來源：** Hacker News | **評分：** 266 | [原文連結](https://arxiv.org/abs/2510.26692)

### 摘要

Kimi Linear 提出了一種混合線性注意力機制，結合 Kimi Delta Attention（KDA）與 Multi‑Head Latent Attention（MLA），在公平比較下超越全 注意力。其專屬的分塊演算法利用對角加低階矩陣（DPLR）實現高硬體效率，同時減少 KV cache 用量達 75%，解碼 throughput 提升至 6 倍。實驗顯示模型在短、長上下文以及強化學習情境中均顯著優於傳統設計，且已開放 KDA 核心與模型檢查點。這項工作展示了在效能與表現之間的最佳平衡點。

**Key Insight:** KDA 結合 DPLR 分塊算法，使得線性注意力在長上下文下既快速又節省記憶體，提供可直接替代全注意力的高效方案。

### 學習筆記

若你在構建Agent或大模型，可考慮採用 Kimi Linear 的 KDA 與 DPLR 實作，以減少 KV cache、提升decode吞吐量，特別適合需要長上下文的應用。

## 5. Before Sending Logs to an LLM, Reduce the Noise Into a Question

`Logs` `LLM` `Observability`

**來源：** DEV.to | [原文連結](https://dev.to/euk_ela_a3e7ed01aa3f7314e/before-sending-logs-to-an-llm-reduce-the-noise-into-a-question-59m5)

### 摘要

這篇文章說明在把日誌交給 LLM 前，必須先過濾噪音，將資訊濃縮成具體問題。它介紹了 open‑source 工具 ctrlb‑decompose，能正規化變數、聚類相似訊息並產生簡潔的 Markdown 或 JSON 輸出，幫助開發者聚焦於關鍵異常模式。作者提醒不要直接使用壓縮後的摘要作為唯一證據，仍需保留原始日誌以作驗證。最終的做法是先提出明確問題，再讓 LLM 提供答案，從而提升診斷效率。

**Key Insight:** 將雜亂的日誌先整理成簡潔的問題，可讓 LLM 更精確地聚焦並產生有用的回應。

### 學習筆記

在處理應用程式日誌時，先使用聚類或變數正規化的方法提煉關鍵異常，然後以明確的問題送給 LLM，最後再驗證原始日誌以確保正確性。
