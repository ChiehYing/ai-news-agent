## 3. A simple fix for LLM tail latency

`LLM` `Latency` `Optimization` `Realtime` `Tail Latency`

**來源：** Hacker News | **評分：** 25 | [原文連結](https://engineering.myhoai.com/posts/a-simple-fix-for-llm-tail-latency/)

### 摘要

當 LLM 呼叫的延遲偶爾極高，直接升級至優先處理 Tier 可能不划算。作者提出對每筆請求發送兩次，取較快的回應，這樣即使標準 Tier 的單次延遲較慢，也能在大多數情況下把最壞情況的等待時間減半。實驗顯示最壞情況的完成時間從約 9.8 秒降到 3.5 秒，甚至把中位數延遲與優先 Tier 持平。這種方法在成本上與升級 Tier 相當，但對真實世界的即時應用（如語音代理）更有效。

**Key Insight:** 重複請求並取較快的回應，往往比付費升級至快速服務更能降低最壞情況的延遲。

### 學習筆記

在開發即時交互式 LLM 系統（例如電話代理）時，先在程式層面實作 "雙重發送" 機制，讓每筆 API 呼叫同時發出兩次，若其中一個回應較快即使用它，這樣即可在不額外購買高價優先 Tier 的情況下顯著改善使用者體驗。

## 9. RAG Agentic: Đếm Và Xếp Hạng Không Phải Việc Của Retrieval

`RAG` `Agent` `Retrieval` `SQL` `Metadata`

**來源：** DEV.to | [原文連結](https://dev.to/bean_bean/rag-agentic-dem-va-xep-hang-khong-phai-viec-cua-retrieval-2mmj)

### 摘要

文章指出在 RAG 系統中，檢索往往需要兩種不同的目標：直接內容查找與聚合統計計算。將這兩種需求混在一起會讓模型在 "計數" 或 "排序" 時產生錯誤。解決方案是建立一層 router，根據查詢類型自動選擇適當的工具：用於內容的混合向量+rerank 搜索，用於聚合的直接 SQL COUNT。這樣可以避免模型自行在原始文本塊上進行統計，提升正確率。作者分享了具體的實作細節，包括 ingestion 時的主題分類與 SQL 查詢生成的批次處理，以及如何在對話輪叫中安全地切換工具。

**Key Insight:** 將檢索需求分為內容查找與聚合統計，並根據類型路由至相應工具，可顯著提高結果正確性。

### 學習筆記

在設計自己的 RAG 系統時，實作一個智能路由層，根據使用者查詢是要找具體段落還是要做統計，分別呼叫經過向量檢索或直接執行 SQL，避免讓大型語言模型在原始文字上自行計數。

## 10. Model Không Còn Là Vấn Đề: OpenCode, Cursor Hay Copilot?

`Coding Agent` `OpenSource` `Workflow` `Terminal` `Model Selection`

**來源：** DEV.to | [原文連結](https://dev.to/bean_bean/model-khong-con-la-van-de-opencode-cursor-hay-copilot-51g3)

### 摘要

文章論述代碼代理的關鍵不在於模型本身的大小或基準測試分數，而在於它是否能理解與尊重專案的慣例與工作流程。開源代理如 OpenCode 能夠完全控制上下文傳遞，開發者可自訂規則使其先讀 CONTRIBUTING.md、優先處理 src 目錄等，從而在實際開發中更符合團隊慣例。相較之下，Cursor 和 Copilot 等專有工具雖然設定簡單但缺乏透明度，且往往綁定於特定 IDE，使得開發者必須改變既有的工作流程。作者建議以實驗衡量代理在真實任務中的 setup 時間、對既有 terminal 工作流程的干擾程度以及在一週後仍需手動修正的次數，以決定最適合的工具。

**Key Insight:** 代理的效能在於它能否融入團隊的慣例與工作流，而不是僅看模型大小或排行榜分數。

### 學習筆記

在評估 coding assistant 時，先測試它是否能自動讀取專案的樣式指南、是否支援在 terminal 中直接執行指令，並觀察使用後需要的人工修正次數，選擇最能無縫融入現有流程的解決方案。
